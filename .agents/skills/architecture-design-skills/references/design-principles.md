# 架构设计重点

## 架构思维

图书公开内容归纳：架构由结构、架构特性、决策与设计原则共同描述；只写风格名称不足以解释系统。架构思维关注技术选择的取舍、业务驱动及与实现团队的协作；方案说明为什么选择、接受什么代价，并随约束变化复评。

## 质量目标

从业务流程、不变量、负载、预算与团队约束推导关键特性：性能、可用性、扩展性、可部署性、可修改性、安全等。只对影响选择的特性排序，不追求所有特性最优。

每个关键目标说明业务理由、优先级、作用范围、指标、负载或故障条件、验证方法。延迟分位数、吞吐、恢复时间与数据丢失容忍度按实际需求选择，目标值来自需求或测量；假设明确标注。

图书预览强调：特性来自领域关注点、显式需求和隐含领域知识；保持关键清单简短。先统一定义，再将“敏捷”等复合目标拆为可修改性、可部署性、可测试性等可评估目标。

工作区自编示例：将“高峰也能下单”拆为指定负载下的尾延迟、吞吐与失败率；将“不能丢订单”拆为已确认写入的持久性、恢复与核对要求。目标表最小字段为：`业务理由 | 特性与优先级 | 作用范围 | 指标及条件 | 验证与证据`，未知数值暂缺。

特性可以作用于一个模块、服务或关键路径；共享存储和同步调用会扩大耦合及故障影响。仅当独立部署或特性作用范围影响选型时分析架构量子（architecture quantum），不把每个服务机械等同一个量子。

补充定义：架构量子用于讨论可以独立运作或部署的一组组件及其耦合作用范围；分析时包含必需的数据与运行依赖，并区分静态依赖和动态交互。不要仅按仓库、进程或服务数量计数。自编检查：某服务停止后，哪些业务与质量目标一同失效，哪些仍可完成？这用于发现影响范围，不能单独证明部署独立性。

## 组件与依赖

图书预览将模块描述为相关代码的集合，组件是模块的物理打包形式；库、包等并不必然独立运行。工作区按下列概念分析边界：

| 概念 | 本地说明与决策影响 |
|---|---|
| 内聚 | 一个模块内的职责是否共同服务同一业务责任、是否一起变化；无关变化频繁牵连时重新划分 |
| 耦合 | 模块对其他模块契约、实现或运行状态的依赖；同时分析改动传播、发布协调和故障传播 |
| connascence | 细分耦合的一组概念：名称、类型、含义、位置、算法等静态关联，以及执行顺序、时机、值、对象身份等动态关联；按强度、距离和参与数量判断影响 |
| 技术分区 | 按展示、业务、数据访问等技术职责组织；共同领域修改可能穿越多个技术分区 |
| 领域分区 | 按业务能力组织，每个领域内再分技术职责；需要明确公共契约与共享责任 |

connascence 的强度表示发现或重构难度，距离表示关联是否跨越较远边界，参与数量表示受牵连的实体数量。跨模块采用更易理解、影响更小的关联；复杂关联尽量限定在职责紧密的局部。此分类来自补充资料，不要求所有项目打分或计算完整指标。

- 根据用例与变化责任识别组件，分配业务流程后检查内聚、依赖与粒度，必要时调整；按业务边界组织，不机械按实体或表拆服务。
- 区分逻辑模块、源码依赖、运行时调用与物理部署。依赖无环；跨模块通过明确契约协作，公共模块仅承载真实共享责任。
- 业务依赖稳定契约，基础设施实现并由组装处注入；基础设施依赖领域接口是依赖倒置，不能用运行时调用箭头判断 import 方向。
- 保留清晰职责，简单场景可合并实现；新增层、接口或模式应解决实际变化、隔离或复用问题，避免空转发和预设框架。

组件识别采用工作区流程：按用例列出初始组件 → 分配责任与数据 → 检查耦合、关键特性和粒度 → 调整边界。自编示例：订单与通知经“订单已提交”契约协作；通知故障能否不阻断已提交订单，应由业务要求与可靠交付机制共同保证。

## 通信与数据

- 明确数据拥有者、读写权限、业务不变量与事务边界；共享数据库需限定跨模块写入责任，独立数据存储需设计跨边界一致性。
- 同步交互说明期限、失败传播和可接受的依赖；异步交互说明持久化、确认、重复、顺序、重放、积压和契约演化。
- 分布式边界引入网络和部分失败；按业务要求选择重试、幂等或可靠补偿，不能用架构风格替代具体正确性机制。

工作区分布式检查：不要假设网络可靠、延迟为零、带宽无限、网络安全、拓扑不变、只有一个管理方、传输无成本或环境同质。对应考虑超时与结果未知、负载、认证、发现和版本兼容、责任归属、跨边界费用与协议差异。
