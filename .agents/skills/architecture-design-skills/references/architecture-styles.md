# 架构风格与选型

通常比较 2—3 个有竞争力的候选，依据质量目标、成本、团队能力与迁移代价取舍；用户已指定或约束已排除其他方案时可缩减。以下场景与边界为工作区选型建议，不能代替实际需求和测量。

| 风格 | 核心结构与适用场景 | 关键边界与代价 |
|---|---|---|
| 分层 Layered | 按技术职责分层；常规业务、部署简单 | 明确允许越过的层；警惕空转发层及跨领域耦合，独立扩容能力有限 |
| 管道 Pipeline | 管道连接过滤器；导入、转换、校验流程 | 定义输入输出、背压、失败与重放；阶段耦合、积压和恢复增加成本 |
| 微内核 Microkernel | 稳定核心与插件；产品扩展、规则或渠道差异 | 定义注册、契约版本、依赖和隔离；核心膨胀与插件兼容增加维护成本 |
| 基于服务 Service-Based | 粗粒度领域服务独立部署；部分独立发布需求 | 基本形态可共享数据库，需约定数据责任和 Schema 兼容；共享数据与服务间协作限制独立性 |
| 事件驱动 Event-Driven | 事件经 broker 分发或 mediator 协调；异步、多订阅者 | 定义事件语义、顺序、重复、重放与失败责任；一致性和调试更复杂 |
| 基于空间 Space-Based | 处理单元与内存数据网格；已证实的存储瓶颈、弹性压力 | 设计分片复制、持久化与故障重建；内存成本、数据冲突和恢复复杂度高 |
| 编排驱动 SOA | 编排引擎组合共享服务；企业跨系统流程 | 约定服务契约与编排状态恢复；共享服务和中央编排可能形成耦合与瓶颈 |
| 微服务 Microservices | 围绕领域与数据责任独立部署；发布、扩容或团队自主需求 | 服务拥有数据并通过契约协作；网络、跨服务一致性、发布与运维成本高 |
| 模块化单体 Modular Monolith | 统一部署、领域模块封装；业务边界清晰而部署隔离收益有限 | 公共契约与数据访问边界需约束；部署、进程资源及扩容仍共享 |

单体/分布式描述运行与部署，技术/领域分区描述逻辑组织；风格可混合，需说明作用范围。管道和插件也可跨进程，不根据局部实现直接给整个系统贴风格标签。

架构风格规定整体拓扑和约束，架构模式解决可组合的问题，代码模式组织局部实现。MQ 不自动构成事件驱动，多个进程不自动构成微服务；Adapter、Option、Repository 等沿用语言或平台资料。CQRS、编排/协同只在相应问题出现时讨论，不默认与某一风格绑定。

## 本地概念说明

公开预览确认的核心结构对应文末来源；更深入的边界说明与检查项为工作区设计说明，不表示已获取完整章节。

- **分层**：按展示、业务、持久化等技术职责形成横向层。封闭层要求调用经过该层，开放层允许跳过；逐层声明规则，避免既禁止越层又要求无意义转发。逻辑层可以同进程部署，不能由层数推导独立扩容能力。
- **管道**：过滤器承担独立处理步骤，管道传递前一步输出，基本形态是单向、点对点。自编示例：`读取记录 → 校验 → 转换 → 写入`。步骤仅依赖输入输出契约；失败恢复要考虑已经写入或已经向下一步交付，不能假设重放没有副作用。
- **微内核**：核心提供运行所需的最小能力，插件承载扩展逻辑。自编示例：稳定的文档处理核心通过契约调用不同格式解析插件。注册表定位插件，契约约束调用与版本；插件互相依赖或大量特例进入核心，会削弱独立扩展收益。
- **基于服务**：基本拓扑为独立 UI、粗粒度领域服务和共享数据库；各服务独立部署，容器化不是必要条件。共享数据库降低部分数据协调成本，却可能让 Schema 变更和跨服务写入牵连其他服务；明确所有权，不能将其视为数据完全隔离的微服务。
- **事件驱动**：组件异步响应已经发生的事实，可以独立采用，也可嵌入其他风格。broker 分发事件、消费者自行响应，流程分散；mediator 持有流程协调逻辑并安排处理步骤，流程更集中但协调者的耦合与恢复责任增加。事件如“订单已提交”与命令如“提交订单”分开定义，选型不能只看是否使用 MQ。
- **基于空间**：目标是减少数据库在高并发关键路径上的瓶颈。处理单元承担业务与内存数据，数据网格组织复制或分片；持久化路径将变化写回长期存储。热路径减压伴随内存成本、数据碰撞与节点恢复复杂度；它不等于普通缓存，也不能只凭流量大就采用。该拓扑解释保留为工作区说明，书籍正文细节待核。
- **编排驱动 SOA**：编排引擎组织多个企业共享服务完成业务流程；集中复用可能扩大契约、发布及运行时耦合。对现有集成系统分析编排状态、共享服务与中央瓶颈；不将其自动设为新系统默认。公开预览主要呈现历史背景与对过度共享的批评，详细服务分类待核。
- **微服务**：围绕限界上下文划分责任。限界上下文限定业务术语和模型的适用边界，不等于一张表或一个实体；实施时说明独立发布、数据责任及跨服务契约。发布独立但业务关键路径依赖多个同步服务时，仍需评估共同故障影响。
- **模块化单体**：功能按领域模块组织、整体作为一个部署单元；模块可以具有内部技术分层。公共契约和数据访问规则限制模块之间的实现耦合；收益是逻辑可修改性，代价是仍共享发布与进程资源。以后拆服务需重新证明通信、一致性与运维收益。

风格是整体拓扑和约束，模式是特定问题的可复用解决方式，工具是实现手段。工作区补充：CQRS 分离读写模型或处理路径，不必然要求分库、事件溯源或微服务；编排由协调者安排流程，协同由参与者通过事件推进流程。选择机制后仍需确定失败与数据责任。
